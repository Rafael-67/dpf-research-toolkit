# DPF Variable Dictionary

> **Architectural consolidation — 23 July 2026.** The current Dictionary
> defines one structured hybrid instrument. References below to separate entry
> workflows are historical compatibility notes only. New evaluations use
> structured observations, independent ordinal ratings, required
> `reasoningSummary`, optional `extendedComments`, field summaries, versioned
> candidate taxonomies and schema `1.2`.
>
> Governance records are normative: `UserProfile` (UUID, pseudonym,
> functional role, active flag, creation time), `EvaluatorAssignment` (UUID,
> study/round/scenario/evaluator IDs, status, creation time),
> `ConsensusRecord` (UUID, hierarchy IDs, field, source-session IDs, reviewer,
> human decision, rationale and lock time), and append-only `AuditEvent`
> (UUID, action, entity, actor, timestamp and details). Current evaluation
> states are `not_started`, `in_progress`, `submitted`,
> `returned_for_revision`, `resubmitted`, `locked`,
> `included_in_analysis`, and `excluded_from_analysis`; exclusion requires a
> justification. Legacy states remain import-compatible.

> **Structured-quantitative alignment — 23 July 2026.** Instrument v1.1 uses
> the complete structured-primary hybrid schema in the current implementation
> brief. Canonical `BaseObservation` properties are `observationId`,
> `taskPhases`, `category: Selection<string>`, `evidenceSources:
> EvidenceSourceSelection[]`, `ratings: QuantitativeObservationRatings`,
> required `reasoningSummary` (maximum 500 characters; 80–300 recommended), and
> optional `extendedComments` (maximum 2,000 characters). Ratings are separate
> 1–5 `analyticalRelevance`, `evidenceStrength`,
> `expectedInfluenceOnDeliveredProtection`, `evaluatorCertainty`, and optional
> `consensusPriority`; they must never be summed or treated as a biological-risk
> or containment score.
>
> The complete additive F1-F6 interfaces and enum catalogues in the brief are
> formally included in this Dictionary. They extend rather than replace every
> value already present here or in the Structured Response Specification. JSON
> selection shape is always `{ value, otherText? }`. Normalised CSV mappings
> and validation rules are enumerated in `SCHEMA_CONSISTENCY_REPORT.md`.
>
> `FieldSummaryRating` contains `fieldId`, `dominantCategories`, four separate
> 1–5 ratings, required `reasoningSummary`, and optional `extendedComments`.
> `TaxonomyReview` contains `taxonomyItemRatings`, `missingItems`, and
> `redundantItems`. Relevance, clarity, distinctiveness, expected frequency,
> missing context, replacement and comments remain separate variables. Only
> explicit relevance ratings may support content-validity calculations.
## Delivered Protection Framework — Variable Specification

**Status:** Current version covers DPF Instrument v1.0 variables in full; DPF Instrument v2.0 variables marked as `[v2.0 — pending Phase 0]`.  
**Purpose:** Defines every measurable variable in the DPF instrument with sufficient precision for independent implementation. Any group using this dictionary should produce an instrument that generates compatible data.  
**Format:** For each variable: name, instrument version, field, type, scale/values, definition, operationalisation, example, scientific rationale, references.

---

## Part A — Scenario metadata variables

These variables characterise the scenario, not the evaluator's response.

---

### `scenarioId`
- **Version:** v1.0
- **Type:** String (unique identifier)
- **Values:** Free text, e.g., "demo-E2"
- **Definition:** Unique identifier for this scenario within the study
- **Notes:** Auto-generated by the platform. Human-readable component optional.

---

### `scenarioVersion`
- **Version:** v1.0
- **Type:** String
- **Values:** Semantic version string, e.g., "1.0"
- **Definition:** Version of the scenario description used in this evaluation round
- **Notes:** Append-only; editing a scenario in use creates a new version. Never overwrite.

---

### `frameworkVersion`
- **Version:** v1.0
- **Type:** String
- **Values:** e.g., "0.1.0-draft"
- **Definition:** Version of the DPF Instrument conceptual framework active at the time this evaluation session began
- **Notes:** Copied at session start. Allows detection of sessions that span a framework revision.

---

### `fieldDefinitionVersions`
- **Version:** v1.0
- **Type:** Object `{F1: string, F2: string, F3: string, F4: string, F5: string, F6: string}`
- **Values:** One version string per field
- **Definition:** The definition version of each individual field at session start
- **Notes:** Enables per-field comparability checking across rounds. A breaking change to F3's definition does not invalidate F1–F2 data from sessions straddling the change.

---

### `isDemo`
- **Version:** v1.0
- **Entity:** Scenario
- **Type:** Boolean
- **Definition:** Whether this scenario is a built-in fictional scenario distributed with the platform (as opposed to a scenario created by the administrator via the UI). `true` means the scenario is part of the platform's canonical fixture set and uses only fictional content. It does not mean the scenario is unsuitable for use in a real evaluation round — `isDemo: true` scenarios are the recommended starting point for Phase 0 studies.
- **Disambiguation:**
  - `isDemo: true` ≠ "this is a toy/demo-only scenario." It means "this scenario ships with the platform."
  - `isDemo: true` does NOT imply fictional data that would invalidate results. All scenarios in DPF-RP are fictional by design.
  - `isDemo: true` is NOT a filter for excluding sessions from analysis. Use `scenarioClass` and `referenceSet` for that purpose.
  - A future field `isBuiltIn` could replace `isDemo` with clearer semantics if needed in v2.0.
- **Constraint:** Must be `true` for all scenarios in `study-config-aligned.json` and `study-config-exploratory.json`. Administrator-created scenarios should default to `false`.

## Part B — Session-level variables

---

### `evaluatorPseudonym`
- **Version:** v1.0
- **Type:** String
- **Values:** Free text (evaluator-chosen, not system-assigned)
- **Definition:** A pseudonymous identifier chosen by the evaluator at session start
- **Constraint:** Must not be a real name, email address, or any identifier traceable to an individual. The platform must accept any string; the administrator is responsible for pseudonymisation protocol.
- **Example:** "EXPERT-BSO-01", "E3"

---

### `institutionCode`
- **Version:** v1.0 (optional field, admin-configurable)
- **Type:** String (categorical)
- **Values:** Admin-defined codes, e.g., "SITE-01", "SITE-02"
- **Definition:** Pseudonymised code for the evaluator's home institution or organisational unit
- **Notes:** Optional; activated by administrator. Never a real institution name.

---

### `professionalProfile`
- **Version:** v1.0 (optional, admin-configurable)
- **Type:** Categorical
- **Values:** biosafety professional / laboratory operator / ergonomist / human-factors specialist / occupational-health professional / other
- **Definition:** The evaluator's primary professional background
- **Notes:** Enables subgroup analysis (do biosafety professionals and ergonomists produce different profiles?).

---

### `experienceLevel`
- **Version:** v1.0 (optional, admin-configurable)
- **Type:** Ordinal
- **Values:** < 2 years / 2–5 years / 6–10 years / > 10 years
- **Definition:** Years of professional experience in the stated professional profile domain

---

### `evaluationStatus`
- **Version:** v1.0
- **Type:** Categorical (state machine)
- **Values:** not_started / in_progress / in_review / completed / abandoned
- **Definition:** Current completion state of the evaluation session
- **Transition rules:**
  - `not_started → in_progress`: on first field answered
  - `in_progress → in_review`: on entering the review screen
  - `in_review → in_progress`: on editing a field from the review screen
  - `in_review → completed`: on final submission after closing survey
  - `in_progress / in_review → abandoned`: set on next app load if session left open > 24h without completion
  - `completed → (terminal)`: no further transitions

---

### `startedAt` / `finishedAt` / `reviewedAt` / `abandonedAt`
- **Version:** v1.0
- **Type:** ISO 8601 UTC timestamp string
- **Definition:** Timestamps for key session lifecycle events
- **Notes:** All timestamps are UTC. `reviewedAt` = time of entering the review screen (first entry; not updated on subsequent back-navigations).

---

### `totalDurationSeconds`
- **Version:** v1.0
- **Type:** Integer (seconds)
- **Definition:** Elapsed time from `startedAt` to `finishedAt`
- **Notes:** Computed at export. Includes time spent on all fields, review screen, and closing survey.

---

### `fieldDurations`
- **Version:** v1.0
- **Type:** Object `{F1: integer, F2: integer, F3: integer, F4: integer, F5: integer, F6: integer}` (seconds)
- **Definition:** Time spent on each field screen
- **Notes:** Measured from field screen entry to navigation away. Does not include time spent on the review screen or closing survey. Not shown to the evaluator during the session.

---

### `completionStatus`
- **Version:** v1.0
- **Type:** Categorical
- **Values:** complete / incomplete (missing_fields) / incomplete (abandoned)
- **Definition:** Whether all required fields were completed before the session ended

---

### `editCount`
- **Version:** v1.0
- **Type:** Integer (per field: `{F1: n, F2: n, …}`)
- **Definition:** Number of times the evaluator returned to a field and made a change after first completing it
- **Notes:** Auto-recorded. Operationalises revision behaviour.

---

### `fictionalScenarioConfirmed`
- **Version:** v1.0
- **Type:** Boolean
- **Definition:** Whether the evaluator explicitly confirmed they understood the scenario as fictional before session export
- **Constraint:** Sessions where this is `false` must be flagged in exports and excluded from analysis by default.

## Part C — Field-response variables (per field, F1–F6)

The following variables exist for each of the six fields. Prefix with field ID: e.g., `F2_relevance`, `F2_narrativeAnswer`.

---

### `{Fn}_narrativeAnswer`
- **Version:** v1.0 primary; v2.0 optional
- **Type:** String (free text)
- **Definition:** The evaluator's substantive narrative response to the field prompt
- **Constraint:** Never used as input to κ or any quantitative analysis. Treated as qualitative data for researcher interpretation.
- **Example (F2):** "Post-spin resuspension requires sustained forearm stability, fine wrist flexion control, and maintained visual focus on an approximately 1mm pellet…"

---

### `{Fn}_relevance`
- **Version:** v1.0
- **Type:** Ordinal (1–4)
- **Scale:**
  - 1 = Not relevant to this task
  - 2 = Slightly relevant
  - 3 = Moderately relevant
  - 4 = Highly relevant
- **Definition:** The evaluator's rating of how relevant this field is to assessing the described task
- **Use in analysis:** Primary input to I-CVI (content-validity index). κ computed across evaluator panel.

---

### `{Fn}_clarity`
- **Version:** v1.0
- **Type:** Ordinal (1–4)
- **Scale:**
  - 1 = Very unclear / very difficult to interpret
  - 2 = Somewhat unclear
  - 3 = Mostly clear
  - 4 = Very clear
- **Definition:** The evaluator's rating of how clear and unambiguous the field prompt is
- **Use in analysis:** Phase 0 instrument-revision trigger. Low clarity ratings identify prompts requiring revision.

---

### `{Fn}_exhaustiveness`
- **Version:** v1.0
- **Type:** Ordinal (1–4)
- **Scale:**
  - 1 = The field misses most important aspects of this domain
  - 2 = The field misses some important aspects
  - 3 = The field captures most important aspects
  - 4 = The field captures all important aspects
- **Definition:** The evaluator's rating of whether the field captures all important aspects of its domain
- **Use in analysis:** Phase 0 instrument-revision trigger. Low exhaustiveness ratings identify fields requiring additional sub-dimensions (Phase 0 → v2.0 structured item design).

---

### `{Fn}_redundancy`
- **Version:** v1.0
- **Type:** Ordinal (1–4)
- **Scale:**
  - 1 = No redundancy — this field captures content not covered elsewhere
  - 2 = Minor overlap — small overlap with another field but clearly distinct
  - 3 = Moderate redundancy — substantial overlap with at least one other field
  - 4 = High redundancy — content is largely duplicated in another field
- **Definition:** The evaluator's rating of whether this field's content overlaps substantially with other fields in the instrument
- **Use in analysis:** Phase 0 instrument revision. High redundancy ratings identify candidate field merges or scope reductions. Fields rated ≥3 by a majority of evaluators are candidates for consolidation.

---

### `{Fn}_applicability`
- **Version:** v1.0
- **Type:** Ordinal (1–4)
- **Scale:**
  - 1 = Not applicable — this field does not apply to the described scenario
  - 2 = Marginally applicable — this field is tangentially relevant to the scenario
  - 3 = Moderately applicable — this field is relevant but not central to this scenario
  - 4 = Fully applicable — this field is directly and substantially relevant to this scenario
- **Definition:** The evaluator's rating of whether this field is applicable and meaningful for the specific scenario being evaluated
- **Use in analysis:** Scenario-level coverage analysis. Low applicability ratings (1–2) identify which fields are less relevant for certain scenario types, informing scenario selection and field-weighting decisions in later phases.

---

### `{Fn}_interpretationDifficulty`
- **Version:** v1.0
- **Type:** Ordinal (1–4)
- **Scale:**
  - 1 = Not difficult
  - 2 = Slightly difficult
  - 3 = Moderately difficult
  - 4 = Very difficult
- **Definition:** The evaluator's rating of how difficult this field was to interpret and complete
- **Use in analysis:** Instrument burden; Phase 3 usability metric. Fields rated ≥3 by majority of evaluators are candidates for redesign.

---

### `{Fn}_confidenceRating`
- **Version:** v1.0
- **Type:** Ordinal (1–4)
- **Scale:**
  - 1 = Very low confidence
  - 2 = Low confidence
  - 3 = Moderate confidence
  - 4 = High confidence
- **Definition:** The evaluator's confidence in their own response to this field
- **Use in analysis:** Weighting consideration for sensitivity analyses. Low-confidence responses may be treated as partial data.

---

### `{Fn}_insufficientInformation`
- **Version:** v1.0
- **Type:** Boolean
- **Definition:** Whether the evaluator flagged this field response as based on insufficient information provided in the scenario
- **Use in analysis:** Exclusion flag. Sessions with `true` for a given field are excluded from that field's κ computation. Never coded as a substantive category.
- **Notes:** Flagging this does not invalidate the session — other fields remain analysable.

---

### `{Fn}_openComment`
- **Version:** v1.0
- **Type:** String (free text)
- **Definition:** The evaluator's qualitative notes on this field (clarity, ambiguity, potential improvements)
- **Use in analysis:** Qualitative analysis for Phase 0 instrument revision.

---

### `{Fn}_changeProposal`
- **Version:** v1.0
- **Type:** String (free text)
- **Definition:** The evaluator's proposed change to this field's prompt, structure, or scale
- **Use in analysis:** Primary input to Phase 0 instrument revision process.

---

## Part D — Field 3 structured variables (v1.0 optional, v2.0 required)

### `F3_exposureRoutes`
- **Version:** v1.0 (optional), v2.0 (required)
- **Type:** Multi-select categorical
- **Values:** aerosol / splash_droplet / percutaneous / surface_contact / environmental
- **Definition:** The exposure routes applicable to the described release scenario
- **Notes:** Multiple selection permitted.

### `F3_releaseScenarioTypes`
- **Version:** v2.0
- **Type:** Multi-select categorical
- **Values:** motor_control_error / omission / sequencing_error / identification_error / equipment_failure
- **Definition:** The type of performance deviation that leads to the described release scenario

### `F3_ergonomicContextSeverity` `[v2.0 — pending Phase 0]`
- **Version:** v2.0
- **Type:** Ordinal (0–3)
- **Scale:**
  - 0 = No link: the ergonomic demand does not plausibly affect this release pathway
  - 1 = Weak link: demand could marginally increase probability
  - 2 = Moderate link: demand is a plausible contributing factor
  - 3 = Strong link: demand is central to the release pathway at this step
- **Definition:** The evaluator's rating of how much the ergonomic demand at this step increases the plausibility of the described release scenario
- **CRITICAL CONSTRAINT:** This variable is NOT a biological risk rating. It measures the ergonomic contribution to a specific release-scenario plausibility. It must not be combined with Field 4 material characteristics to produce a risk index. Platform display must label this variable as "ergonomic contribution to release-scenario plausibility" and never as "risk" or "severity."

- **Type:** Categorical

### `F4_concentrationLevel` `[v2.0 — intratask comparison only]`
- **Type:** Ordinal (0–3)
- **Scale (intratask, not absolute):**
  - 0 = Lower than other phases in this task
  - 1 = Unchanged relative to other phases
  - 2 = Higher than other phases in this task

### `F4_volumeLevel` `[v2.0 — intratask comparison only]`
- **Type:** Ordinal (0–3)
- **Scale (intratask, not absolute):**
  - 0 = Lower than other phases in this task
  - 1 = Unchanged relative to other phases
  - 2 = Higher than other phases in this task
  - 3 = Not comparable / single-phase material contact
- **Definition:** Same rationale as concentration — intratask comparison only.

## Part H — Closing survey variables

### RTLX subscales
- `rtlx_mental` / `rtlx_physical` / `rtlx_temporal` / `rtlx_performance` / `rtlx_effort` / `rtlx_frustration`
- **Type:** Integer (0–100, standard NASA published scale)
- **Notes:** Standard Raw TLX wording verbatim. No lab-adapted phrasing. Applied per scenario (non-standard use — see DPF Instrument Specification v1.0 §7).

### SUS items
- `sus_item_01` … `sus_item_10`
- **Type:** Integer (1–5, standard SUS Likert scale)
- **Notes:** Standard SUS wording verbatim. Applied per scenario (non-standard use — visible in-app notice required).

### `sus_score` (computed)
- **Formula:** Standard SUS scoring: sum of (item_n − 1) for odd items + (5 − item_n) for even items, × 2.5
- **Range:** 0–100
- **Notes:** Reported as descriptive statistic. No threshold ("good" / "poor") applied automatically.

### Open feedback
- `feedback_burden` / `feedback_ambiguity` / `feedback_usefulness`
- **Type:** String (free text)
- **Definition:** Evaluator qualitative feedback on instrument burden, main ambiguity, and perceived usefulness

## Part I — Agreement statistics (computed, not captured per evaluation)

These variables exist at the round level, not the session level.

### `kappa_cohen_pairwise`
- **Type:** Float (−1 to +1), per evaluator pair, per field, per rating variable
- **Formula:** Cohen (1960)
- **Validated against:** Landis & Koch (1977) worked example

### `kappa_fleiss_panel`
- **Type:** Float (−1 to +1), per field, per rating variable, for ≥3 evaluators
- **Formula:** Fleiss (1971)
- **Validated against:** Fleiss (1971) worked example

### `percent_agreement`
- **Type:** Float (0–100%), per field, per rating variable
- **Formula:** (number of agreements / total possible agreements) × 100

### `ICVI`
- **Type:** Float (0–1) `[v2.0]`
- **Formula:** Number of evaluators rating relevance ≥ 3 / total evaluators (for panels of ≥5)
- **Threshold:** I-CVI ≥ 0.78 (Lynn, 1986) for item retention in v2.0
- **Note:** Not applicable in v1.0 (narrative responses; only rating variables are quantified)

### Landis & Koch interpretive bands (displayed alongside κ, never applied automatically)

| κ range | Label |
|---|---|
| < 0.00 | Poor |
| 0.00–0.20 | Slight |
| 0.21–0.40 | Fair |
| 0.41–0.60 | Moderate |
| 0.61–0.80 | Substantial |
| 0.81–1.00 | Almost perfect |

## Appendix A — Standard item wording (verbatim, not to be adapted)

### Raw Task Load Index (RTLX) subscale wording

Use the following wording **verbatim** for all six subscales. No laboratory-adapted phrasing.

| Variable | Label | Prompt text (verbatim) | Low anchor | High anchor |
|---|---|---|---|---|
| `rtlx_mental` | Mental Demand | How much mental and perceptual activity was required? Was the task easy or demanding, simple or complex, exacting or forgiving? | Low | High |
| `rtlx_physical` | Physical Demand | How much physical activity was required? Was the task easy or demanding, slack or strenuous, restful or laborious? | Low | High |
| `rtlx_temporal` | Temporal Demand | How much time pressure did you feel due to the pace at which tasks or task elements occurred? Was the pace slow and leisurely or rapid and frantic? | Low | High |
| `rtlx_performance` | Performance | How successful were you in accomplishing the goals set by the experimenter (or yourself)? How satisfied were you with your performance? | Good | Poor |
| `rtlx_effort` | Effort | How hard did you have to work (mentally and physically) to accomplish your level of performance? | Low | High |
| `rtlx_frustration` | Frustration | How irritated, stressed, and annoyed versus content, relaxed, and complacent did you feel during the task? | Low | High |

All subscales: 0–100 continuous or 21-point (0, 5, 10, … 100). DPF-RP implements 0–100 slider. Standard Raw TLX — no pairwise weighting step.

---

### System Usability Scale (SUS) item wording

Use the following wording **verbatim** for all ten items. No adaptation. Likert scale: 1 (Strongly disagree) → 5 (Strongly agree).

| Variable | # | Item text (verbatim) |
|---|---|---|
| `sus_item_01` | 1 | I think that I would like to use this system frequently. |
| `sus_item_02` | 2 | I found the system unnecessarily complex. |
| `sus_item_03` | 3 | I thought the system was easy to use. |
| `sus_item_04` | 4 | I think that I would need the support of a technical person to be able to use this system. |
| `sus_item_05` | 5 | I found the various functions in this system were well integrated. |
| `sus_item_06` | 6 | I thought there was too much inconsistency in this system. |
| `sus_item_07` | 7 | I would imagine that most people would learn to use this system very quickly. |
| `sus_item_08` | 8 | I found the system very cumbersome to use. |
| `sus_item_09` | 9 | I felt very confident using the system. |
| `sus_item_10` | 10 | I needed to learn a lot of things before I could get going with this system. |

**Scoring:** (item_01 − 1) + (5 − item_02) + (item_03 − 1) + (5 − item_04) + (item_05 − 1) + (5 − item_06) + (item_07 − 1) + (5 − item_08) + (item_09 − 1) + (5 − item_10), then × 2.5. Range: 0–100.

**Non-standard use notice (required in-app):** *"Note: The SUS is designed as a single end-of-session measure. In this study, it is administered once per scenario to measure the burden of applying the six-field instrument to each specific task — this is a non-standard use. Interpret results accordingly and report this limitation in any publication."*

Source: Brooke, J. (1996). SUS: A "quick and dirty" usability scale. In P. Jordan et al. (Eds.), *Usability Evaluation in Industry*. Taylor & Francis.

## Appendix B — Scenario classification fields (v1.1+)

These three fields extend the `Scenario` entity to distinguish reference scenarios (E1–E5) from research-extension scenarios (ORG-01, INC-01 and any future exploratory additions). They are optional with defined defaults to preserve backwards compatibility with existing `study-config.json` files that do not contain them.

---

### `scenarioClass`
- **Version:** v1.1 (optional with default)
- **Entity:** Scenario
- **Type:** Categorical string
- **Values:** `"reference"` | `"research-extension"` | `"user"`
- **Default when absent:** context-dependent (see rule below)
- **Default rule:**
  - If the scenario was **imported** from a JSON file (i.e., it existed before the current session and lacks a `scenarioClass` field): default = `"reference"` — preserves backward compatibility with pre-v1.1 canonical configs
  - If the scenario was **created by the administrator via the platform UI** in the current session: default = `"user"` — prevents UI-created scenarios from being silently classified as reference
  - If the `scenarioClass` field is **explicitly present** in the imported JSON: use the declared value regardless of import source
- **Definition:** Classification of the scenario into one of three tiers. `"reference"`: belongs to the aligned reference set (E1–E5) shared across S1, S2, and DPF-RP — these are the Phase 0 content-validation scenarios. `"research-extension"`: an exploratory scenario (ORG-01, INC-01) that is not part of the E1–E5 reference set and did not participate in the same design process. `"user"`: any scenario created by an administrator that does not belong to either canonical set. The default `"user"` ensures that no user-created scenario is ever automatically classified as a reference scenario
- **Display:** The platform must show a visible label to the evaluator and administrator on the scenario-selection screen. Suggested labels: "Reference scenario" / "Research-extension scenario"
- **Export:** Must appear in every exported evaluation session JSON and merged dataset CSV as a column derived from the parent scenario
- **Backwards compatibility:** A `study-config.json` imported without this field is treated as if all scenarios carry `scenarioClass: "reference"`. No error; no prompt.

---

### `referenceSet`
- **Version:** v1.1 (optional with default)
- **Entity:** Scenario
- **Type:** Boolean
- **Values:** `true` | `false`
- **Default when absent:** `true`
- **Definition:** Whether this scenario is part of the aligned reference set described in Supplementary Materials S1 and S2 of the accompanying manuscript
- **Constraint:** Must be `false` for any scenario with `scenarioClass: "research-extension"`. A scenario with `referenceSet: true` and `scenarioClass: "research-extension"` is a validation error — the platform must reject it on import.
- **Use in analysis:** Enables downstream filtering: analysts can split the merged dataset by `referenceSet` to separate primary validation data from exploratory data without relying on `scenarioId` naming conventions.

---

### `studyAlignment`
- **Version:** v1.1 (optional)
- **Entity:** Scenario
- **Type:** String (free text, controlled vocabulary recommended)
- **Recommended values:** `"primary-reference"` | `"separate-exploratory-round"` | `"pilot"` | `"other: [description]"`
- **Default when absent:** `null`
- **Definition:** A human-readable note describing the intended relationship between this scenario and the primary validation study
- **Notes:** Informational only. Not used for filtering or computation. Intended for administrators who need to explain the provenance of a scenario set to evaluators or collaborators. If `referenceSet: false`, this field should explain why the scenario is not part of the reference set.
- **Example:** `"Exploratory extension; not part of primary Phase 0 validation; see DPF_INSTRUMENT_ROADMAP_v2.md"`

---

### Backwards-compatibility import rule (platform enforcement)

When importing a `study-config.json` that predates v1.1:

1. Any scenario missing `scenarioClass` → treat as `"reference"`, log in import summary
2. Any scenario missing `referenceSet` → treat as `true`, log in import summary
3. Any scenario missing `studyAlignment` → treat as `null`, no log needed
4. No import error; no user prompt; import proceeds normally
5. The import summary (shown to the administrator after a successful import) must state: "N scenario(s) imported without classification fields; treated as reference scenarios by default."

observations are an optional enrichment layer.

### `{Fn}_noObservationReason`
- **Version:** v1.1
- **Type:** Categorical string | null
- **Values:** `"insufficient_information"` | `"field_not_applicable"` | `null`

### Shared enumerated types

#### `TaskPhase`
- `"pre_task_preparation"`
- `"initial_phase"`
- `"intermediate_phase"`
- `"final_phase"`
- `"critical_sub_step"`
- `"transition"`
- `"interruption"`
- `"resumption"`
- `"whole_task"`
- `"other"` (with free text)

#### `AnalyticalRelevance`
- `"low"` — the observation may be real but has little bearing on the
  Delivered Protection analysis for this task
- `"moderate"` — contributes to the analysis but is not a determining factor
- `"high"` — directly relevant to understanding how ergonomic or
  organisational conditions interact with biological containment at
  this task
- `"undetermined"` — insufficient information to assess

**Label in UI:** *"Analytical relevance within this field"*
**Help text:** *"Rate how important this observation is for
interpreting the current field. This is not a biological-risk or
protection-level score."*

#### `EvidenceSource`
- `"scenario_information"` — stated in the scenario description
- `"sop_documentation"` — referenced SOP or procedural document
- `"operator_interview"` — would require direct operator input
- `"electronic_record"` — audit trail, log, or timestamp system
- `"instrumental_measurement"` — sensor, wearable, or imaging
- `"evaluator_inference"` — reasoned from available information
- `"insufficient_information"` — key information is missing
- `"other"` (with free text)

#### `EvaluatorCertainty`
Renamed from `Certainty` to clarify that this measures the evaluator's confidence in their own assessment, **not** the availability of documentary evidence (which is captured by `evidenceSources` and `evidenceSufficiency`). An expert inference may warrant high certainty; a direct scenario statement may warrant low certainty if it is ambiguous.

- `"high"` — the evaluator is confident in this assessment given the available information and their professional expertise
- `"moderate"` — the assessment is plausible but the evaluator has meaningful uncertainty about its accuracy
- `"low"` — the assessment is speculative; the evaluator would revise it substantially given more information

### `Other — specify` handling rules

`Other — specify` is an analytic data source, not an escape valve.
The platform must:

1. Store `otherCategoryText` in full alongside the observation
2. Export it in every CSV and JSON export under column
   `{field}_obs_{n}_other_category_text`
3. Make it searchable and filterable in the administrator merge view
4. NOT merge it silently with any existing category
5. Report the count of `isOtherCategory: true` per field in the
   round summary — this frequency is a primary Phase 0 output

The research team reviews `Other — specify` entries after each round
to determine whether any merit promotion to a formal category. Each
reviewed entry must be explicitly marked as one of:
- `incorporate` → add to taxonomy in next version
- `merge` → assign to existing category with rationale
- `retain_other` → keep as open text; insufficient frequency or clarity
- `discard` → not relevant to this field
